## 一、30 秒项目一句话介绍

> 本项目基于 CWRU 公开轴承数据集，构建了一个 B/S 架构的轴承故障智能监测与诊断系统：通过振动信号预处理、特征提取与随机森林分类实现四类故障（正常/内圈/滚动体/外圈）自动诊断，结合健康趋势预测与知识推理，输出可解释的运维决策，并支持诊断记录持久化。

---

## 二、演示流程（建议 5-8 分钟）

1. **启动**：`python web/app.py` → 浏览器打开 `http://127.0.0.1:5000`（30 秒）
2. **数据加载**：选内圈故障 IR021_3_212 → 加载 → 展示波形/频谱（1 分钟）
3. **故障诊断**：点击诊断 → 内圈故障 99.6% 重度 → 紧急停机告警 + 知识推理建议（1.5 分钟）
4. **健康预测**：点击预测 → 趋势图 + 健康度 35.3 → 预警判定（1 分钟）
5. **对比演示**：切正常数据 normal_0_97 → 诊断 99.8% 正常 → 波形差异对比（1 分钟）
6. **记录展示**：诊断记录、告警记录（30 秒）

## 三、可能被问的问题与回答

### Q1：为什么用随机森林？为什么不用深度学习（CNN/LSTM）？
**答**：课程设计要求兼顾"可解释性"和"工程落地"。随机森林基于 20 维手工特征（12 时域 + 8 频域），训练快、无需 GPU，准确率 0.997（随机划分）/ 0.891（5 折 CV）已满足要求，且特征重要性可解释故障机理。深度学习在数据量充足时更优，但需要更多数据与调参成本，适合作为后续扩展方向。

### Q2：数据泄漏问题是怎么发现的？怎么解决的？
**答**：滑动窗口重叠（步长 512 < 窗口 1024）导致相邻窗口高度相关。最初随机划分评估准确率虚高到 0.997，但按**文件分组（GroupShuffleSplit）**后真实泛化能力约 0.633，说明随机划分存在严重信息泄漏。正确做法是按数据文件划分训练/测试集，模拟"未见设备"的真实场景。这一结论已写入阶段三报告。

### Q3：置信度是怎么算的？
**答**：对信号滑动窗口提取全部特征矩阵，对每个窗口取 `predict_proba`，求平均后取最大概率值作为置信度，对应类别作为诊断结果（多窗口投票）。

### Q4：健康度和预警阈值是怎么设定的？
**答**：以振动信号 RMS 作为健康指标，滑动窗口构建健康退化序列，多项式回归外推 30 步。阈值基于健康序列基线（如均值+倍数标准差）动态计算，当预测值超过阈值判定预警。健康度归一化到 0-100。

### Q5：数据库为什么用 SQLite？
**答**：课程设计单机部署场景下，SQLite 零配置、单文件、够用且便于提交答辩，避免 MySQL/服务器部署的复杂度。四张表（sensor_data/fault_sample/fault_knowledge/alarm_record）与方案设计 3.6 一致。

### Q6：数据是从哪里来的？合规吗？
**答**：CWRU 凯斯西储大学公开数据集（engineering.case.edu/bearingdatacenter），README 已写明引用链接，完全公开免费。遵循"公开数据引链接、自建数据先开源再引用、私有敏感数据不用"的规范。

### Q7：系统的局限和改进方向？
**答**：局限：① 数据仅下载 20 个文件（B/OR 样本偏少），按文件分组泛化能力待提升；② 单通道（驱动端）；③ 健康预测为统计外推，非机理模型。改进：补全数据、多通道融合、引入深度学习、接入实时采集。

## 四、核心亮点（答辩强调）

1. **严谨的实验方法论**：发现并正确处理了数据泄漏，按文件分组评估真实泛化能力；
2. **完整的闭环系统**：从数据 → 算法 → Web → 可视化 → 知识推理 → 记录持久化全链路；
3. **可解释的智能诊断**：诊断结果 + 严重度分级 + 成因/处理建议/检查清单，贴近工业运维实际；
4. **工程化细节**：多窗口投票稳定置信度、大数据量抽稀优化、前端资源本地化保障离线演示。
