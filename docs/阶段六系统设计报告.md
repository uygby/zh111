## 1. 系统总体架构

系统采用 **B/S（浏览器/服务器）三层架构**：

```
┌─────────────────────────────────────────────────────────┐
│  表现层（浏览器）                                        │
│  HTML + CSS + JavaScript + ECharts + Bootstrap           │
│  波形图 / 频谱图 / 健康趋势图 / 诊断结果 / 运维建议       │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP / REST API (JSON)
┌──────────────────────────┴──────────────────────────────┐
│  应用层（Flask Web 服务）                                 │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌──────────┐ │
│  │ 数据 API  │ │ 诊断 API  │ │ 预测 API  │ │ 推理/记录 │ │
│  └───────────┘ └───────────┘ └───────────┘ └──────────┘ │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────┴──────────────────────────────┐
│  算法层（src 模块，Python）                               │
│  预处理 → 特征提取 → 分类模型 → 健康预测 → 知识推理       │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────┴──────────────────────────────┐
│  数据层                                                   │
│  CWRU 原始 .mat 数据 │ SQLite（诊断/告警/知识库）          │
└─────────────────────────────────────────────────────────┘
```

**设计原则**：
- **前后端分离**：前端通过 REST API 异步获取数据，ECharts 负责可视化；
- **算法模块解耦**：Web 层仅调用 `src/` 中已实现的算法函数，不重复实现业务逻辑；
- **数据持久化**：诊断记录、告警记录、知识库持久化到 SQLite，支持历史追溯。

## 2. 模块设计

### 2.1 Web 后端（web/app.py）

| 模块 | 职责 |
|---|---|
| 数据接口 | 数据集列表、信号/频谱读取（抽稀 3000/1500 点） |
| 诊断接口 | 调用预处理+特征提取+模型预测+知识推理，写入记录 |
| 预测接口 | 调用健康预测模块，返回趋势序列与预警判定 |
| 推理接口 | 知识推理与知识库查询 |
| 记录接口 | 诊断/告警记录查询 |

**关键实现——多窗口投票**：诊断时对信号滑动窗口提取特征矩阵，对所有窗口取 `predict_proba` 均值再取最大概率类，相比单窗口预测显著提升稳定性。

### 2.2 SQLite 数据库（web/database.py）

四张表（对应方案设计 3.6）：

| 表名 | 字段 | 用途 |
|---|---|---|
| `sensor_data` | timestamp, device_id, channel, vibration_value | 振动传感器时序数据 |
| `fault_sample` | sample_time, label, fault_type, feature_vector, confidence | 故障样本记录 |
| `fault_knowledge` | fault_type, name, cause, features_desc, advice, checks | 故障知识库（4 条，UNIQUE） |
| `alarm_record` | timestamp, device_id, alarm_type, description | 告警记录 |

### 2.3 前端（templates/index.html + static）

| 组件 | 说明 |
|---|---|
| 数据选择面板 | 数据集下拉框（20 文件）+ 加载/诊断/预测按钮 |
| ECharts 波形图 | 驱动端 DE 振动波形（3000 点抽稀，含缩放） |
| ECharts 频谱图 | 0~6000Hz 幅值谱 |
| ECharts 趋势图 | 历史健康指标 + 趋势预测 + 预警阈值三线叠加 |
| 健康度面板 | 当前健康度与预警状态实时联动 |
| 诊断结果/运维建议 | 故障名称、代码、严重度、置信度、成因、处理建议、检查清单 |
| 记录表格 | 诊断记录、告警记录实时刷新 |

## 3. 核心流程

### 3.1 故障诊断流程

```
用户选择数据 → 点击【故障诊断】
  → GET /api/signal 加载波形展示
  → POST /api/diagnose:
      signal → 预处理(带通滤波/去趋势/滑动窗口/z-score)
            → extract_features 20维特征矩阵
            → 随机森林 predict_proba 多窗口投票
            → reason() 严重度分级 + 运维建议
      → INSERT fault_sample；中重度 → INSERT alarm_record
  → 前端渲染诊断结果 + 知识推理建议 + 告警横幅
```

### 3.2 健康趋势预测流程

```
用户点击【健康趋势预测】
  → POST /api/predict:
      signal → 滑动窗口构建 RMS 健康序列
            → 多项式回归外推 30 步
            → 计算健康度(0-100)、预警阈值判定
  → 前端渲染三线趋势图 + 健康度 + 预警状态
```

## 4. 关键技术点

### 4.1 大数据量前端展示优化（抽稀）
原始信号最长约 24 万点，直接传输会卡顿。后端采用**等间隔抽稀**：
- 波形：抽稀至 3000 点；
- 频谱：先计算全量 FFT，取 0~6000Hz 后抽稀至 1500 点。

### 4.2 模型稳定化（多窗口投票）
```python
X = extract_features(windows)          # 全部窗口的特征
proba = MODEL.predict_proba(X)         # 各窗口概率
avg_proba = proba.mean(axis=0)         # 平均
pred = MODEL.classes_[argmax(avg_proba)]
confidence = avg_proba.max()
```

### 4.3 知识推理与严重度分级
诊断结果送入知识库，按峭度等特征分级（峭度≥8 重度、≥5 中度），并匹配四类故障的成因/处理建议/检查清单，输出可解释的运维决策。

### 4.4 前端资源本地化
ECharts 下载至本地 `web/static/js/echarts.min.js`，避免 CDN 不可达导致页面白屏，保障离线演示可用。
